Governed Agentic RAG

Measuring the Safety–Cost Trade-off of a Governance Layer
🏫 CCE IISc · LLMs – A Hands-on Approach 👥 Himani Ponia & Vinita Sharma 📅 August 2026 gemma4:12b-mlx 🤖 Apple MacBook M4 · MLX runtime
Executive Summary

This project wraps a planner → retriever → validator → generator agentic RAG pipeline in a governance layer of four pluggable controls (C1–C4) and runs a controlled ablation on HotpotQA (500 questions, 4,937 documents + 4 PoisonedRAG-style poison docs) to quantify exactly what safety each control buys and what it costs in latency and tokens. The model is gemma4:12b-mlx served via Ollama on an Apple M4 with MLX acceleration, using BAAI/bge-small-en-v1.5 embeddings (384-dim) and an on-disk Qdrant vector store.

Headline result: full governance drives the unauthorised-disclosure leak rate from 100 % → 0 %, poison exposure from 100 % → 0 %, and audit completeness from 0 % → 100 %, while the composite latency under full governance is actually lower than the ungoverned baseline because C1's ACL filter reduces the context sent to the LLM.

3. Per-Control Analysis
C1 Permission-aware Retrieval
Leak rate
0.000
was 1.000 (−100%)
Token reduction
−41%
769 → 450 prompt tokens

The ACL filter lives at the vector layer — restricted chunks (finance dept, class=restricted/internal) are blocked before they ever reach the prompt. In the demo: 3 finance-owned chunks were leaked to an HR caller without C1; 0 with C1 on. The latency drops 17 % and prompt tokens drop 41 % because fewer chunks enter the context window. This is the most impactful single control.

C3 Injection / Poison Screen
Poison exposure
0.000
was 1.000 (−100%)
Latency overhead
+7.5 s
regex scan + extra call

Regex heuristics screen every retrieved chunk for injected instructions: "ignore previous instructions", "system notice", "the assistant must append", "reply only with ANSWER:…", and 11+ patterns. In the demo: 2 poisoned chunks appeared in context without C3; with C3 on — 0 reached the generator. Limitation: paraphrased injections not matching the pattern list can evade the screen.

C2 Grounding / Citation Gate
Latency overhead
+17.5 s
most expensive control
Faithfulness (measured)
0.000*
claim extraction issue

C2 runs post-generation: it splits the answer into claims, verifies each against the retrieved evidence passages in a single batched LLM call, and hard-rejects ungrounded claims. The grounding gate added 17.5 s (38 %) latency — the highest overhead of any individual control. Measured faithfulness is 0 due to claim extractor parse failure with this model's output style (see §5).

C4 Tamper-evident Audit Log
Audit completeness
100%
every retrieval logged
Latency overhead
~0 s
hash computation is free

Every pipeline step (retrieval → C1 → C3 → PII → generate → C2) is recorded as a hash-chained JSON record: hash = sha256(prev_hash + canonical_json(record)). Tampering any field breaks the chain (demonstrated live — see §4). Overhead is negligible. This control should always be shipped — near-free forensics.

5. Safety–Cost Trade-off
Composite safety score vs. latency overhead

* Composite safety = mean of (1−leak_rate), (1−poison_exposure), (1−injection_success), audit_completeness. Faithfulness excluded from composite because of the measurement limitation below. Top-right corner = best: highest safety, lowest latency.

Key trade-off observations
  • C1 is the best deal: leak rate −100 pp, latency −17 % (cheaper than baseline), tokens −41 %. Filters at the vector layer so the generator never pays for restricted context.
  • C3 costs ~7 s for the regex scan but eliminates 100 % of poison exposure. Pattern-based so it is CPU-local and deterministic.
  • C2 is the most expensive control: +17.5 s (+38 %) for claim verification LLM calls. Its benefit (faithfulness gate) is partially obscured by the claim extraction limitation. Budget explicitly before enabling.
  • C4 is near-free: <1 s overhead for SHA-256 hash computation and JSON serialisation. 100 % audit completeness at negligible cost.
  • Full governance is faster than +C2 alone: C1's prompt reduction outweighs C2's verifier overhead when both are combined (38.4 s vs. 63.2 s for +C2 only).

6. Limitations & Known Issues
Faithfulness = 0 (C2 grounding)
⚠
The audit log entry for C2 reads: grounded 0/0 claims (backend=llm). The sentence-level claim splitter is not extracting verifiable claims from gemma4:12b-mlx outputs. This means: (1) faithfulness is not being measured, (2) C2 unconditionally rejects (no claims = no grounding = reject). Fix: tune the claim extractor regex or switch to an NLI-based splitter that operates on the raw text without requiring structured list output.
injection_success = 0 everywhere
ℹ
injection_success measures whether a canary string literally appears in the model's generated answer. gemma4:12b-mlx does not literally repeat the injected phrase (e.g. "ANSWER: 42") even when the poison chunk is in context. This is expected behaviour — a stronger/more instruction-following model might comply. The more meaningful metric is poison_exposure (did the chunk reach context?), which C3 reduces to 0.
Other limitations
  • C3 heuristic-only: Paraphrased or encoded injections (e.g. base64, Unicode confusables, indirect phrasing) are not covered by the current regex pattern list. A semantic classifier or dedicated guardrail model would be needed for production.
  • Small corpus: 500 HotpotQA questions → 4,937 docs is sufficient for a controlled experiment but not representative of a production RAG corpus with millions of documents.
  • Deterministic ACL assignment: Role permissions are synthetic (hash-bucketed), not derived from a real enterprise RBAC policy. Real-world ACL complexity is higher.
  • Single-hop only: The planner executes a single retrieval round. True multi-hop reasoning (iterative retrieval) is stubbed but not evaluated.
  • Local-only latency: MLX on M4 is fast for generation but CPU for embedding. A production system with GPU inference would have different relative overhead profiles.
7. Design Recommendations
Backed by measured numbers
  1. Enforce ACL at the vector layer (C1), not the application layer. Measured: leak rate 100% → 0%, latency −17%, tokens −41%. Application-layer filtering (post-retrieval) lets restricted chunks into the context window first.
  2. Screen retrieved chunks before the context window (C3), not after generation. Post-hoc output filtering cannot un-see content the LLM has already processed. C3's pre-generation screen reduces poison exposure to 0 at a fraction of C2's cost.
  3. Ship C4 always — it's near-free. Hash-chained audit with <1 s overhead enables incident forensics, compliance evidence, and tamper detection. There is no reason to omit it.
  4. Budget C2's grounding gate explicitly. At +38% latency it is the most expensive control. It is valuable for faithfulness enforcement but requires a capable claim extractor and judge model to be meaningful.
  5. Use poison_exposure, not injection_success, as the primary C3 KPI. Whether the LLM complies with the injection depends on the model; whether the chunk reached context is deterministic. Measure what you can control.
